# Optimization register

These are source-guided candidates. Adoption requires measured costs, independent numerical acceptance and matched same-stream timings.

| Candidate | Removable work and current evidence | Constraint and scope | Discriminating test |
| --- | --- | --- | --- |
| Read both collections together | The original 20,000-entry file carries both jet containers and shared event metadata. Separate input traversals can read the same metadata twice. | Compatible. Changes reader and object layout. | Compare two standalone jobs with a combined job. Record branch union, unique compressed bytes, per-collection outputs and elapsed phase times. Check whether peak memory and chunk sizes change. |
| Share uncertainty evaluation | Both configurations initialize JetUncertaintiesTool, including ordinary and pseudo-data instances. The configuration and payload differ by jet definition. | Compatible. Shared numerical routines must be parameterized by the exact release data and statuses. | Count actual group evaluations and time the two collections separately. Compare common implementation cost with collection-specific group, table and branch populations. |
| Share nominal results across variations | A state can change a subset of downstream quantities. The stock run produced two small-radius weight-only states and a separate mass-resolution family for large-radius jets. | Compatible. A dependency map is required per state. | Count recalculation, selection, weights and RNG draws per original jet. Check full-state, subset, order and chunk invariance. |
| Keep large-radius mass resolution independent | The active release calls a distinct forward-folding tool with large-radius truth association and a response map. | Compatible. Collection-specific implementation. | Measure the truth-match and response phases, then test reuse of only the quantities invariant under the source contract. |
| Keep NNJVT feature and inference costs identifiable | Small-radius jets have a momentum-dependent tagging and scale-factor chain, including two dedicated weight states. | Compatible. Collection-specific stage with possible reuse across states. | Count evaluated networks, features, cuts, scale-factor lookups and pass/fail branches before choosing reuse or batching. |

### First full-file screen

Each of five focused comparisons passed the independent 32-event object observer, with small and large checked separately for the projected payload. Each of the 13 complete 20,000-event runs then reproduced the corresponding original histogram. Cells give a single elapsed time in seconds. [Inputs, scopes, observer receipts and times](evidence/diagnostics/trials/screen-001.json)

| Mechanism changed in isolation | Small-R | Large-R | Combined | Decision at screening |
| --- | ---: | ---: | ---: | --- |
| Portable baseline | 20.78 | 6.00 | 21.96 | Control |
| Read arguments directly in the uncertainty plugin | 22.85 | 6.07 | 22.68 | Drop this implementation. Its repeated accessor calls cost time in all three jobs. |
| Cache standard Gaussian by positive seed | 17.49 | 5.88 | 18.48 | Advance to the independent full gates and repeated controls. |
| Load a prebuilt single-radius payload | 20.60 | 4.61 | — | Advance the one-wheel equivalent for qualified comparisons. |
| Reuse identical nominal NNJVT update inputs | 21.37 | — | 20.86 | Signs differ across the two applicable scopes. Use one bounded repeated comparison at the new cache checkpoint. |

The resolution cache uses 1,048,576 bytes per execution thread. On the complete small-R job it served 3,968,802 hits and 1,352,612 misses. Four negative first variates required the original ordered rejection loop. The large-R job recorded 173,296 hits, 14,084 misses and no restarts. This leaves a measurable small-R opportunity for a larger table, with a fourfold memory tradeoff. Four synthetic binaries, comprising both scalar and cached versions of both random backends, independently passed 83,270 exact ROOT comparisons apiece. [Small-R counters](evidence/diagnostics/cache-use/small.json) · [Large-R counters](evidence/diagnostics/cache-use/large.json) · [ROOT fixture](evidence/diagnostics/rng-fixture/portable-cache.check.txt)

The generic CorrectionLib default batch loop copies numeric broadcast values and the scalar systematic string into the row argument vector. After the slower specialized trial, the candidate generic fix keeps only owned constants across rows while rereading every borrowed or strided numeric input. The separate histogram candidate removes the variable-axis search used solely to classify flow before interpolation. Those flow-clamp searches account for 285 of the 11,040 baseline CPU samples. The larger EtaJES storage candidate targets two TH1F correction nodes containing 118.64 MB of decimal JSON with exact original binary32 bin values. These candidates have distinct build or payload identities. ### Selecting the final stack

The last 48 jobs held the physical chunk at 1,000 entries for small-R and combined, and 4,000 for large-R. The common prefix provider already included the 4 MiB cache, direct flow classification and support for signed siblings. Adding the separate large-R truth cache made the large-R mean 2.819 s. Adding the irregular-axis index as well gave 2.835 s. Their separate earlier gains do not add. In the combined jobs the complete stack had the lowest retained mean with signed evaluation, and all three paired observations were faster than the signed prefix-only jobs. The small-R difference between those two native builds was 0.35%. We selected one provider with both mechanisms and signed reuse enabled for the small-R and combined workflows. Large-R alone uses ordinary state evaluation. ### Does avoiding argument copies help?

The installed Python profile attributed 129,220 flat-array copies to the CorrectionLib call boundary. In the single-worker combined job, 48,838 arguments representing 2,285,023,832 cumulative bytes met ownership, dtype and layout requirements for borrowing. The general API retained copied snapshots because its native evaluator releases the Python GIL. The control and treatment used the same visible script, shipped libraries and scope-dependent materialization. Every full-file result matched its independent stock histogram. [Eligibility](evidence/diagnostics/contiguous-arguments/eligibility.json) · [Layout and snapshot fixture](evidence/diagnostics/contiguous-arguments/fixture.json) · [First 24 jobs](evidence/diagnostics/contiguous-arguments/first-comparison.json)

The control and candidate averaged 11.065 ± 0.065 and 11.027 ± 0.106 s for small-R, and 12.827 ± 0.039 and 13.052 ± 0.262 s combined. All three combined pairs favored the existing copy. Large-R initially failed the candidate spread check. A bounded eight-job large-R repeat passed both spread checks. The three retained control jobs averaged 2.805 ± 0.020 s and the candidate 2.907 ± 0.007 s. Keep the existing copy policy. This final comparison gives one resolved small-gain or negative combined result. The remaining opportunities need additional attribution, ownership contracts or a changed execution rule. ### End-to-end improvement of the shipped workflow

Thirty-six fresh commands compared the uncached release-backed faithful path, packed wheel 005 and shipped wheel 006 using the original random stream. All commands read the 20,000 original events and reproduced their stock histogram. The physical branch identities matched across all three implementations within each radius and matched the production grid. Three retained wall times per implementation and scope passed the spread limits. Small-R moved from 54.251 to 13.824 to 11.282 s, large-R from 12.142 to 3.698 to 2.805 s, and joint processing from 60.622 to 15.235 to 12.919 s. The shipped workflow was 4.81×, 4.33× and 4.69× faster than the faithful implementation, respectively. These comparisons measure the whole delivered configurations, including materialization and process startup.
